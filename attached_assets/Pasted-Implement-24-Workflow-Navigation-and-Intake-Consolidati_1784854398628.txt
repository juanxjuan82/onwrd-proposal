# Product model

The product has two primary operating destinations:

1. **Opportunities** — potential work before ONWRD commits to developing a proposal
2. **Proposals** — committed proposal work from development through Google handoff

**Team Review is a proposal lifecycle phase, not a standalone sidebar destination.**

All intake sources must converge into one canonical Opportunity or, for a blank proposal, directly into one Proposal. Do not maintain separate proposal-generation pipelines for each intake source.

# Public prospect-intake submission

Preserve `/intake` as a public, no-sidebar route.

The current `/api/intake` endpoint automatically calls AI—up to three attempts—and generates a complete Proposal. Remove that behavior entirely.

New submission cycle:

1. Validate the prospect’s form.
2. Parse permitted PDF/DOCX/TXT uploads using the existing limits.
3. Preserve the complete formatted brief and extracted file text.
4. Create exactly one Opportunity.
5. Apply deterministic scoring.
6. Mark and link the intake draft.
7. Notify ONWRD with a link to `/opportunities/{id}`.
8. Return only `{ success: true }`.
9. Show the prospect the existing confirmation experience.

The submission must:

* Create zero Proposals
* Make zero AI calls
* Make zero Google API calls
* Never expose the internal Opportunity ID to the prospect
* Never log prospect PII, uploaded text or full request bodies

Suggested Opportunity mapping:

* `title`: project type and organization, falling back to `Project inquiry — {organization}`
* `agency`: organization
* `description`: prospect’s project description
* `category`: selected industry
* `valueAmount`: selected investment range
* `contactInfo`: contact name, title, email, phone and preferred method
* `rawText`: full formatted intake plus extracted document text
* `status`: normal new-opportunity status
* `sourceType`: `prospect_intake`

If no source discriminator exists, add a nullable `sourceType` column rather than misusing `sourceUrl`.

Add a nullable `opportunityId` foreign key to `intake_drafts`. Preserve the existing `proposalId` column for legacy compatibility.

Use the intake draft or an explicit submission key for idempotency. A repeated submission must return success without creating another Opportunity.

Creating the Opportunity and linking/marking the intake draft must be transactional.

The existing implementation extracts uploaded text but does not persist the original binary. Preserve the extracted text. Do not claim that the original attachment is stored unless a secure storage implementation already exists.

# Canonical Pursue transition

The current code has conflicting `start-bid` and `convert` behaviors. Replace them with one canonical idempotent transition:

`POST /api/opportunities/:id/pursue`

Required behavior:

1. Validate the Opportunity.
2. Create or retrieve exactly one Proposal for it.
3. Use the existing unique relationship/constraint to prevent duplicates.
4. Mark the Opportunity In Progress.
5. Link the Opportunity and Proposal consistently.
6. Return the Proposal ID.
7. Frontend navigates immediately to `/proposals/{proposalId}`.
8. Make zero AI calls.
9. Do not start `runExtractionPipeline`.
10. Do not automatically extract requirements, generate strategy or generate a draft.

Use a transaction or equivalent atomic protection so concurrent Pursue requests cannot create duplicates.

Remove all frontend calls to `start-bid` and `convert`.

For backward compatibility, either:

* Keep the old endpoints as deprecated wrappers around the same no-AI Pursue service, or
* Return an intentional redirect/deprecation response if no callers require them.

Under no circumstances may the old `convert` endpoint continue launching background extraction.

Tests must prove that repeated and concurrent Pursue calls return the same Proposal.
