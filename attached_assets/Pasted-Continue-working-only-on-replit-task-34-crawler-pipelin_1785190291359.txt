## 1. Fix the crawl batch-ID race

The current POST `/api/tender-intelligence/crawl` starts `runCrawler()` and then queries the latest `crawl_batches` row. This can return the previous completed batch ID, causing the frontend to poll stale state and finish before the active crawl completes.

Refactor the lifecycle so that:

* The current batch ID is generated before background work starts.
* The exact batch row is persisted before the endpoint responds.
* That batch ID is passed directly into the crawl executor.
* The endpoint returns that exact ID with `202 Accepted`.
* Never query the latest batch row to infer the current batch.
* Remove the 300ms polling loop and completion-assigned local `batchId` variable.
* Concurrent crawl requests return `409` when the crawl lock cannot be acquired.
* Any failure after lock acquisition marks the correct batch failed and releases the lock through a comprehensive `try/finally`.

Add tests proving:

* Two consecutive crawls return two distinct IDs.
* Each response ID belongs to the crawl it started.
* An older completed batch can never be returned for a new crawl.
* Lock contention returns `409`, not `202` with a stale or null ID.
* Startup/source-query failures mark the batch failed and release the lock.
