A. Fix the canonical Proposal generation flow

Current bug:
- Pursue creates the canonical Proposal with proposalContent = "".
- proposal-detail.tsx calls POST /api/opportunities/:id/generate-proposal with { proposalId }.
- That backend endpoint ignores proposalId and inserts another Proposal.
- The UI remains on the original empty Proposal, and the unique tender_id constraint may make generation fail entirely.

Required behavior:
1. POST /api/opportunities/:id/generate-proposal must generate into the existing canonical Proposal linked to that Opportunity.
2. Resolve the canonical Proposal by tenderId inside a transaction.
3. If proposalId is supplied, validate that it belongs to the Opportunity.
4. Never create a second Proposal for the same tender.
5. If no Proposal exists for a legacy caller, create it using INSERT ... ON CONFLICT (tender_id) DO NOTHING, then fetch the canonical row.
6. Update that same Proposal to proposal_drafting.
7. Create or reset its section rows without producing duplicate sections.
8. Run AI generation against that Proposal ID and update the same Proposal and section rows.
9. Return { proposalId, status } using the canonical ID.
10. Make concurrent Generate Draft requests idempotent or return a specific 409 generation_in_progress response.
