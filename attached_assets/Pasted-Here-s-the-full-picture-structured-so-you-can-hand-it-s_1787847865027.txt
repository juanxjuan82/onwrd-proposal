Here's the full picture, structured so you can hand it straight to another agent.

## Architecture: Replit-managed Clerk + server-side domain gate

Google sign-in itself is just Clerk. The "restrict to our company domain" part is **not** a Clerk feature — Clerk has no allowlist setting for that — so it's enforced entirely in application code, on both ends.

### 1. One manual step (not code)
In the target project's workspace, open the **Auth pane** in the toolbar and enable Google as a sign-in provider. Optionally hide email/password if you want Google-only, and optionally swap in the team's own Google OAuth Client ID/Secret for a branded consent screen ("Continue with X" instead of "Continue with Clerk"). This step has to happen in the Auth pane regardless of which project — code can't do it. Point the other agent at the `clerk-auth` skill for the general Replit-managed-Clerk setup; the domain restriction below is a customization on top of that.

### 2. Secrets (auto-provisioned by Replit's Clerk integration)
- `CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY` — backend
- `VITE_CLERK_PUBLISHABLE_KEY` — frontend

### 3. Backend wiring (`artifacts/api-server`)
- **`middlewares/clerkProxyMiddleware.ts`** — proxies Clerk's Frontend API through your own domain in production (avoids CNAME setup for custom domains). No-ops in dev.
- **`app.ts`** — mounts the proxy *before* `express.json()`/`cookieParser()` (it streams raw bytes), then `clerkMiddleware()` with the publishable key resolved dynamically from the request host (supports multiple Clerk custom domains on one server).
- **`lib/admin/auth.ts`** — this is the actual enforcement, `requireOnwrdStaff`:
  1. `getAuth(req)` → 401 if no session.
  2. `clerkClient.users.getUser(auth.userId)` → check `emailAddresses` for one with `verification.status === "verified"` ending in the allowed domain → 403 if none match.
  3. **Key gotcha:** Clerk session claims don't include email by default, so you can't skip step 2 and read it off the session.
- This middleware is applied to every route under `/admin` (see `routes/admin.ts`).

### 4. Frontend wiring (`artifacts/brand-audit`)
- **`App.tsx`** — `ClerkProvider` at the root, publishable key resolved via `publishableKeyFromHost(hostname, VITE_CLERK_PUBLISHABLE_KEY)`, `proxyUrl` from `VITE_CLERK_PROXY_URL` (empty in dev), `signInUrl`/`signUpUrl` pointing at dedicated routes, `routerPush`/`routerReplace` wired into the app's router (wouter here) so Clerk's navigation doesn't fight the SPA router.
- **`pages/sign-in.tsx`** / **`sign-up.tsx`** — thin wrappers around `<SignIn>`/`<SignUp>` from `@clerk/react` with `routing="path"`.
- **`pages/admin.tsx`** gate pattern:
  ```tsx
  <Show when="signed-in"><AdminDashboard /></Show>
  <Show when="signed-out"><Redirect to="/sign-in" /></Show>
  ```
  That only checks "is anyone signed in," not domain. Domain enforcement is the server's `requireOnwrdStaff` — the frontend just reacts to the resulting 401/403 on its data fetch and renders an `AccessRestricted` screen with a "sign out and try another account" button. This is UX only; the server is the source of truth.

## What to change for a different project
Only two things are project-specific:
1. The allowed-domain string in `requireOnwrdStaff` (or swap for a different rule entirely — specific emails, multiple domains, etc.)
2. Which routes get that middleware applied.

Everything else — the proxy middleware, `ClerkProvider` setup, sign-in/sign-up pages, the `Show`/`Redirect` gating pattern, the 401-vs-403 UX split — copies over as-is. The other agent still needs to do the Auth-pane step manually in the new project since that's not something committed to code.
